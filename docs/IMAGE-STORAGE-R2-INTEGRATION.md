# Cloudflare R2 Image Storage Integration Strategy

**Document Status:** Current implementation reference with future work clearly marked
**Target Storage Engine:** Cloudflare R2 (S3-compatible object storage)  
**Current State:** Backend-mediated R2 uploads and delivery are implemented. Static repository assets and legacy IndexedDB image display remain supported.

---

## 1. Executive Summary & Objectives

The Icon Electromatic website is a high-reliability B2B catalog displaying RF, microwave, and electronic components from 15 global OEM partners. Currently:
1. Repository images continue to be served from static paths.
2. The Admin CMS sends image files to the authenticated backend `POST /api/media/upload`; the backend validates, uploads to R2, and stores media metadata in PostgreSQL.
3. Public media is delivered through `GET /api/media/file/:id`. Legacy `idb:` values remain displayable, but a failed R2 upload no longer falls back to IndexedDB.

**Goal:** Establish an enterprise-grade, cost-effective, durable image storage system powered by Cloudflare R2. R2 eliminates egress fees, offers global CDN distribution, and maintains standard S3 API compatibility.

---

## 2. Current Architecture & Preservation Guarantee

### Existing image support
- **Static Assets:** Hardcoded references like `/images/oem-logos/Rogers_Logo_no_bg.png` or `/images/products/image1.jpeg` resolve directly via Vite's public asset pipeline.
- **Legacy IndexedDB Blobs:** Existing values such as `idb:img_<timestamp>_<random>` remain displayable through the existing image resolution support.
- **Upload failure behavior:** A failed R2 upload shows an error and restores the upload control. It does not save an `idb:` URL.
- **Preservation:** Existing legacy IndexedDB data and repository static assets are not automatically purged.

### PostgreSQL Database Schema Alignment
The PostgreSQL schema migration (`20261019233400_add_cms_backend_schema`) provides the exact tables needed for R2 assets:
- **`MediaAsset`**:
  - `id`: Unique cuid identifier.
  - `r2Key`: Unique S3 object key generated by the backend (UUID-based).
  - `publicUrl`: Application media route URL returned to the frontend.
  - `mimeType`: Uploaded image MIME type; the current validator accepts JPEG, PNG, WebP, and GIF.
  - `byteSize`: File size in bytes.
  - `sha256`: 64-character SHA-256 hex digest recorded with the asset.
  - `status`: `PENDING`, `ACTIVE`, `RETIRED`, `FAILED`.
  - `uploadedById`: Optional relation to `AdminUser`.
- **`ProductMedia`**:
  - `productId`: References `Product.id`.
  - `mediaAssetId`: References `MediaAsset.id`.
  - `sortOrder`: Display sequence in product galleries.
  - `altText`: Accessibility text for SEO.
  - `isPrimary`: Boolean flag indicating primary catalog thumbnail.

## 3. Implemented Cloudflare R2 Architecture

```
┌────────────────────────┐         Direct S3 API           ┌────────────────────────┐
│  Express Backend API   │ ──────────────────────────────> │      Cloudflare R2     │
│   (S3 Client SDK)      │                                 │   Object Storage Bucket│
└────────────────────────┘                                 └────────────────────────┘
            ▲                                                          │
            ▲ Credentials remain server-side                         │
            │                                                         ▼
┌────────────────────────┐   `/api/media/file/:id`         ┌────────────────────────┐
│ Admin CMS / Browser    │ <────────────────────────────── │ Optional public domain│
│ (Vite + Vanilla JS)    │                                 │ only if configured    │
└────────────────────────┘                                 └────────────────────────┘
```

### Bucket Configuration
- **Bucket Name:** `icon-electromatic-media` (separate buckets for staging/production via environment variables).
- **Bucket access:** Keep the bucket private by default. The backend uses S3-compatible credentials held only in its environment.
- **Credentials:** `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`, and `R2_ENDPOINT` are required for the implemented R2 service. Never expose them to frontend code.
- **Optional public domain:** If `R2_PUBLIC_DOMAIN` is set, the delivery route redirects to that host and object key. Otherwise the backend streams from R2 and can fall back to a short-lived signed URL.

## 4. Ingestion & Upload Workflows

### Implemented upload path

1. The admin submits an image to authenticated `POST /api/media/upload`.
2. The backend validates the image's magic bytes (JPEG, PNG, WebP, or GIF) and enforces a 10 MB limit.
3. The backend uploads the object to R2, creates a `MediaAsset` record in PostgreSQL, and attempts to return a short-lived preview URL.
4. If the database record cannot be saved after the R2 upload, the backend attempts to delete the newly uploaded object as compensation.
5. Public delivery uses `GET /api/media/file/:id`. It streams from the private bucket where possible, uses a short-lived signed URL fallback, or redirects to `R2_PUBLIC_DOMAIN` when configured.

Uploads are proxied through the backend; the browser does not upload directly to R2. Therefore, a direct browser-to-bucket CORS configuration is not required for this upload implementation.

### Live R2 integration test safeguards

The test suite's live R2 integration test is skipped by default and in CI. It
performs an upload, object inspection, and deletion only when
`RUN_LIVE_R2_TESTS=true` is explicitly set. Before opting in, use a
client-approved, non-production test bucket: set `R2_TEST_BUCKET_NAME` to that
bucket and make `R2_BUCKET_NAME` match it exactly. The test refuses the known
production bucket `icon-electromatic-media` and passes the verified test bucket
explicitly to each R2 operation. Never use production credentials or enable the
test against a production bucket.

## 5. Future Work: Existing Asset Migration

No automatic bulk migration of repository images or browser IndexedDB blobs is
implemented. The following is a proposal only and must be designed, approved,
and tested separately before any data migration or R2 writes.

### Phase 1: Repository Static Asset Ingestion
A Node.js maintenance script (`backend/scripts/migrate-local-images-to-r2.js`) will:
1. Scan local image directories (`/public/images/products`, `/public/images/oem-logos`).
2. Calculate the SHA-256 checksum and MIME type of each file.
3. Upload to R2 with structured keys:
   - `oem-logos/{sha256[:12]}-{fileName}`
   - `products/{sha256[:12]}-{fileName}`
4. Create corresponding `MediaAsset` records and update `sourceImagePath` / `ProductMedia`.
5. Run in a dry-run preview mode before writing any data.

### Phase 2: IndexedDB Client Asset Migration
For images created during demo admin usage:
1. Upon admin authentication, `ImageStorage` checks for unsynchronized `idb:` keys.
2. The CMS prompts the admin with a synchronization preview: `"3 images stored in your local browser can be uploaded to persistent cloud storage."`
3. Upon approval, blobs are extracted from IndexedDB, uploaded via the pre-signed URL workflow, and their `idb:` keys in catalog records are replaced with persistent `https://media.iconelectromatic.com/...` URLs.
4. The local IndexedDB copy is kept as a cached fallback until confirmed live.

## 6. Future Work: Replacement, Retirement, and Cleanup

- The application has not implemented the proposed retired-asset lifecycle job or
  automatic 30-day purge. Do not assume object versioning, scheduled cleanup, or
  replacement rollback is configured.
- Before adding replacement or deletion automation, define retention, backup,
  restore, and authorization requirements with the client and test them against
  a non-production bucket.

---

## 7. Existing Fallbacks and Recovery Considerations

1. `GET /api/media/file/:id` can fall back from streaming to a short-lived signed
   URL when R2 streaming fails.
2. Existing `idb:` image values remain displayable using the browser's existing
   IndexedDB resolution support; new upload failures are not saved there.
3. R2 object versioning, automated database restoration, and universal fallback
   from failed public CDN image loads are not guaranteed by this implementation.
   The client should configure and test provider backups and recovery policies
   separately. See [DISASTER-RECOVERY-RUNBOOK.md](./DISASTER-RECOVERY-RUNBOOK.md)
   for coordinated database/R2 recovery considerations and the client approval
   gate for recovery actions.

## 8. Deployment Configuration Checklist

- [ ] Create a client-owned bucket and a bucket-scoped Object Read & Write API credential.
- [ ] Configure the R2 endpoint and credential variables only in the backend's secret store.
- [ ] Keep public bucket access disabled unless the client explicitly selects the optional `R2_PUBLIC_DOMAIN` delivery mode.
- [ ] Verify `POST /api/media/upload` and `GET /api/media/file/:id` through a non-production environment before production use.
- [ ] Agree on backup, recovery, retention, and any future bulk migration plan separately.
